## Phase-4 adversarial pass (post-fix), 2026-08-21

A verification pass run against the fixed tree reproduced two bugs the 19-finding wave had left. Both were reproduced against the live DB before being fixed, and both now have regression tests that fail on the old code.

57. ~~**The commit's own rewrite wiped `logged_at`, so a retry or a late item billed a back-dated meal to today** (`resolver/commit.py _commit_one`): the §7.2 shift rides each item's staged jsonb and every rewrite site appends `KEEP_LOG_KEYS_SQL` to preserve it — except the commit rewrite itself, which wrote a bare `staged=%s`. Reproduced live (the spy recorded `[shifted, today, today]`), then `test_phase4_fixes.py::test_commit_retry_and_late_item_still_bill_the_shifted_day`. §7.2 now states the invariant and why a missed site hides.
58. ~~**A saved meal whose foods rows are gone logged half of itself, or claimed it did not exist** (`resolver/cascade.py expand_macro`): a stored item pointing at a missing `foods` row was skipped with a bare `continue`. A 3-item breakfast missing one food expanded into 2 rows and committed as a complete meal — under-counting a day he believes he logged whole — and on the single-row path the surviving item took the `len(rows) == 1` shortcut, logging one food in place of a meal. 59. *(adversarial pass, deferred)* **A broken-macro guard counts as a §9 short-circuit hit.** The guard is staged from `short_circuit_all`, so its log carries `short_circuit = true` while its only item is `needs_input`; `hits_incl_discarded` counts any item on a short-circuited log, so a discarded broken-macro log reads as an alias hit. Narrow (it needs a broken macro *and* a discarded log) and not new for the partial case — the pre-fix truncation counted as a tier-0 hit too — but the honest definition is that a `needs_input` item is never a hit. Fixing it means the hit filter reads the item's own status, not just the log's flag.
60. *(adversarial pass, observed)* **The tier-3 agent sometimes asks a question with zero options.** `test_tier3_live.py::test_quest_bar_branded_or_question` (a real gpt-5.6-terra run, not `live`-marked) failed once and passed on the re-run, 2026-08-21: the failing run returned `needs_input` with *"Which Quest bar flavor or product line was it (for example, Protein Bar Chocolate Chip Cookie Dough, Hero Bar, or a Crispy)?"* and `options: []` — the examples were prose inside the question text instead of the tappable options §3.4 expects. `StagedRow.tsx` renders the text and an empty chip row; the row is still editable, so the escape is tapping it open, not answering the question. Nondeterministic, so the assertion stays as-is (never weakened to get green); the fix, if it recurs, is a prompt-side rule that an option-less question is not an acceptable answer.

61. *(adversarial pass, deferred)* **A when-hint on an item-less log is lost, so a later manual add bills today.** `routes/logs.py _persist` writes the shifted `logged_at` onto item rows, looping over `resolutions` — so when decompose returns a `when_hint` with **zero** items ("yesterday at lunch" with nothing parsed as food), the shift is never persisted anywhere. Adding a food afterwards via `POST /api/resolve` inserts a fresh row with no `logged_at`, and the commit falls back to `captured_at`: the entry lands on today for a meal the user filed to yesterday. Same failure class as item 57, different door — that one lost the stamp on rewrite, this one never writes it. The fix is to stamp the shift at the log level (or onto the log's staged payload) rather than only onto items that happen to exist at staging time.
62. *(adversarial pass, not reachable via the API)* **A macro with an empty `items` array gets the "No saved meal" guard.** `expand_macro` returns `([], 0)`, so neither the `missing` nor the `rows` branch fires and control reaches `MEAL_REF_GUARD` — the same lie item 58 fixed for the missing-foods case, and `short_circuit_all` returns `None` so the utterance falls through to decompose. Recorded for completeness only: `resolver/commit.py validate_meal_items` raises *"a saved meal needs at least one item"* on both `POST /api/meals` and `PATCH /api/meals/:id`, so this state cannot be created through the API — only by writing `meal_macros.items = '[]'` directly.
