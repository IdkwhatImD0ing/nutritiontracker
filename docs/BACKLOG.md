Verified-in-code before fixing is mandatory — reviewers can be wrong. Fixed items get struck through with the phase that fixed them. Sources: Phase 1 adversarial panel (bugs/security/conformance), 2026-08-20. The 6 most severe findings (3 blockers, 3 majors) were fixed in Phase 1's fix pass; these remain.

6. **`/api/resolve` ignores `unit`** and reimplements a divergent tier-1 `pick()` (missing mode-of-last-10) — unify with `resolver/cascade.py`'s implementation (§3.2, §7.3).
7. ~~**Core-macros guard missing** (`resolver/commit.py`): a serving lacking kcal/protein/carb/fat can snapshot partial macros into the diary silently — guard + verify-me instead.~~ *fixed Phase 2* — guard in `resolver/commit.py` (W2); fix-pass completed the user-visible half: refusals now ride the commit response (`CommitResponse.errors`, `routes/commit.py`) and surface as needs-attention pills (`PendingItems`) instead of being silently discarded, and the tier-1/2 staging path (`cascade._stage_resolved`) stages a partial-core-macros serving as verify-me (macros=None, low confidence) instead of crashing with a pydantic ValidationError.

9. **brandOwner ranking not applied** (`sources/fdc.py`): §3.4 requires ranking branded hits by brandOwner (fuzzy-noisy name search).

37. ~~**"Estimation has no code path" was prompt-only for the web lane**: `add_food(source="web")` accepted a model-supplied `source_url`/`citations` with nothing tying them to a search or fetch that happened.~~ *fixed Phase 3* — post-run evidence gate in `run_tier3` (`_web_evidence_gap`): the `source_url` host must appear in this run's `web_search_call.action.sources`/opened urls, `url_citation` annotations, or a successful `fetch_page` (tracked in run state); otherwise the item is demoted to `not_found`, the unreferenced row is dropped (`_discard_web_food`), and the reason is archived in `agent_transcript` as a `usual_web_gate` item (`test_run_tier3_drops_web_food_without_real_evidence`).

39. *(Phase-3 fix-pass, deferred)* The evidence gate is **host-level**, not page-level: the model can still name a different page on the same official host, and the transcribed numbers themselves are not code-verifiable (a prompt-injected page on the pinned domain is the residual). 40. *(Phase-3 fix-pass, deferred)* A gate-demoted item reads as a plain `not_found` to the user — the "couldn't verify the source page" reason lives only in the archived transcript; a user-visible note needs a `StagedItem` field (models.py, contract change).
41. *(Phase-3 fix-pass, deferred)* An already-cached web food cannot be chosen directly from the local candidates: `_get_food_cached`'s web branch reads the run cache only and the prompt allows `source="web"` only for a food just created via `add_food`, so the §3.4 "choose the cached food" rule is dark for web foods (the agent re-searches and re-transcribes; identical values dedup to the same row, transcription jitter creates a near-duplicate). Tier-1 aliases cover the common repeat case.
42. *(Phase-3 fix-pass, observed)* **McDonald's is bot-hostile**: `mcdonalds.com` product pages time out (20 s) for every non-browser client — the app UA and a Chrome UA alike — so `fetch_page` cannot read them, and the hosted `web_search` reader extracts the JS-rendered panel only sometimes (1 of 4 pinned "Big Mac" runs resolved, 2026-08-21; the other 3 ended honestly as `not_found`, never an estimate). Chick-fil-A (server-rendered page, 11.6 s) and Starbucks (search sources, 10.4 s) resolve first try. `fetch_page` now refuses a repeat of a URL that already failed this run (saves a turn + a timeout per retry); the live test keeps "Big Mac" as a non-strict xfail and gates on Chick-fil-A. Options: a headless-browser fetch for JS chains, or seeding the handful of bot-hostile chains from their published PDFs.
